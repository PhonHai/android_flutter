A4 业务流程

  1. 用户点击桌面图标 → MainActivity（Theme.Translucent，单实例）→ 申请 8 项运行时权限 → 通过 ServiceConnection 绑定 VoiceAssistantService。
  2. Service.onCreate：① 预下载离线语音包（阿里云 aar 自带 aijia + 额外下载 xiaoqi）② EventBus 注册 ③ 创建摄像头 1×1 悬浮窗 + AI 助手 gif 悬浮窗 ④ 注册 ConnectivityManager.NetworkCallback ⑤ 拉取阿里云 Token（启动时无网络则 fallback）
  3. Service.onStartCommand → 启动前台（microphone）→ 鉴权 + 初始化 TTS（先 TTS 后 ASR）→ 初始化本地唤醒 → 进入 WAIT_WAKEUP。
  4. 用户说 "小云小云" → NUI EVENT_WUW_TRUSTED → stopWakeup → 切 WAKEUP_SUCCESS → 弹气泡 + 播"你好，请说" → 初始化 ASR → 启动 ASR 监听 → WAIT_REGON。
  5. ASR 回调：onPartialResult（中间结果）实时显示；onFinalResult（最终结果）走 命令优先级链。
  6. 命令优先级链（详见 VoiceAssistantService.handleVoiceCommand）： 
    ① 退出语音助手（"退出助手"等）→ 回到 WAIT_WAKEUP
② 导航选择（导航列表可见时）→ 提取数字选第 N 个 POI
③ 车控（正则 / 中文数字）→ 本地执行 / CarControlSDK
④ App 控制（assets/app_commands.json）→ 启动第三方 App
⑤ 可见即可说（SystemNavigationManager + MyAccessibilityService + 3D）→ 无障碍 API
⑥ 音乐控制（KEYCODE_MEDIA_NEXT...）→ dispatchMediaKeyEvent
⑦ AI 问答 → LLM 流式 → 流式 TTS → 浮窗实时刷新
  7. 流式 TTS onChunk → streamUtil.speak(chunk) → 阿里云 SDK 推流 → AudioPlayer 实时播放 → 浮窗 EVENT_UPDATE_ANSWER_CONTENT 滚动显示。
  8. onPlayFinished → startASRListening() → 多轮对话。
  9. 退出 / 打断路径：EVENT_SWITCH_MODEL / 退出命令 / 流式 cancel → isCancelTask / Thread.interrupt / streamClient.cancelCurrentRequest。

A6 关键设计点

① 4 状态有限状态机，而不是狂用 if/else

枚举 AssistantStatus：WAIT_WAKEUP / WAKEUP_SUCCESS / WAIT_REGON / REGOIN_SUCCESS_AND_RETRY。每个分支/回调都先检查状态，避免 ASR 重复启动、避免 TTS 期间又被 ASR 录到、避免切模型时的竞态。

② 双 ASR 引擎 + 可配置

ConfigManager.getASREngine() 给出 online / offline。在线用阿里云 NUI；离线用讯飞 AIKit（断网或车机弱网场景）。

③ 三条 TTS 通道

在线流式（zhixiaoxia，AI 回调用）/ 离线（aijia/xiaoqi，启动时 ZIP 预下载，弱网兜底）/ 系统 TTS（兜底）。

④ 三 LLM 可热切换

千问（dashscope SDK）、豆包（volcengine ark）、芯擎/端模型（私有）。流式回调统一抽象 ILlmClientStreamService，onChunk 喂给流式 TTS。重问时缓存 lastValidQuestion，切换完直接重发。

⑤ 车控配置驱动

assets/car_commands.json 描述设备 → 操作 → 触发正则 → 动作 → 反馈。新车型只需改 JSON，不重发包。每个操作支持 triggers（固定正则）+ trigger_patterns（带参数）。

⑥ 复合指令 + 中文数字

"打开空调和风量调到三档" → 按"和/与/并且/同时/以及/并"拆 → 动词补全（"调风量"）→ convertChineseNumberToArabic（"三" → 3，处理"十/百/千/万"，"二十六" → 26）。

⑦ 边界检查

温度 16-32°C、风速 0-8 档，超过范围直接语音反馈"超出范围，无法执行"；并基于当前状态计算（getACTemperature/getACWindSpeed）。

⑧ 可见即可说 2D + 3D 双引擎

2D：AccessibilityService 抓节点 + 中文数字 + 包含/相似匹配 + 标准点击 + 坐标手势点击（dispatchGesture 兜底）；3D：CarControlSDK onCallBackVoiceAssistant 把 3D 元素 JSON 推过来，模糊匹配后 setVoiceCommandToAndroid。

⑨ 网络自恢复

ConnectivityManager.NetworkCallback 监听 onAvailable / onLost；断网时切回 WAIT_WAKEUP + 释放 ASR；恢复时重新初始化 TTS（鉴权文件丢失 140008 错误修复）+ 重启唤醒。

⑩ 鉴权 SPA 签名 + 主动刷新

阿里云 Token = HMAC-SHA1（AccessKeySecret + 规范化请求）。AuthHelper.checkTokenIsValidAndUpdate 在 token 剩余 < 2 小时自动续期；token 持久化到 SharedPreferences。

⑪ 全局录音冲突规避

AudioRecord 音源 VOICE_COMMUNICATION（Q+）+ AcousticEchoCanceler 开启；TTS 开始时 stopRecognize；音乐焦点用 AUDIOFOCUS_GAIN_TRANSIENT_EXCLUSIVE。

⑫ 状态机进入路径可追踪

所有 10+ 个"进入等待唤醒监听方法入口"以及 7 个"ASR 启动入口"都用 Log.w("----------第N个入口XXXX---------") 唯一编号，排查"为什么没进入"类问题极快。

难点 / 踩坑

  • 阿里云 NUI 鉴权文件：首次启动无网络 → 唤醒 240088 / TTS 140008 → 监听网络恢复自动重试；离线时还要兜底讯飞 ASR。
  • 流式 TTS 取消：要同时发 cancelStreamInputTts + 强制 audioPlayer.stop() + 同步 isSynthesizing=false；onCancel 回调延迟引发 200ms 重试窗口。
  • ASR 重复启动：通过 isStartingSpeechRecognition 标志位 + synchronized + 状态机检查三重防护。
  • LLM 切模型竞态：EVENT_SWITCH_MODEL 移除上一个切换 runnable + 延迟 300ms 等 onCancel 完成 + 重置 isCancelTask。
  • 悬浮窗权限：Android 12+ 强制 Settings.canDrawOverlays，主流程引导用户开启。
  • 前台服务被 kill：START_STICKY + AlarmManager + 5 秒 PendingIntent 自拉；预留 restartApp（killProcess + Suicide）兜底。
  • 车机型号差异：空调温度最小 16°C、最大 32°C 写死，反馈"超出范围"；预留接口读整车。可扩展成可配置。

考察：逻辑层次、表达能力

追问为什么车机要自研方案？直接用 Android Auto / CarPlay 不行吗？
考察：业务理解
主要三条：① 自主可控——OEM 要深度定制（车控、3D Launcher、整车协议），通用方案根本触达不到 CAN 总线；② 系统级权限——需要 sharedUserId=system + 平台签名，车机预装才有；③ 本地化能力——要求离线唤醒、离线 ASR、离线 TTS，地库隧道没网也得能用，通用方案都依赖云端。一句话：通用方案是"导航播报员"，我们要的是"能开车门、调空调、看 3D 车模的管家"。
深挖这项目里你最得意的是什么？
考察：自我认知、亮点聚焦
三选一讲：
① 4 状态状态机 + 入口序号日志——被 bug 逼出来的设计，每个入口都打"第 N 个进入等待唤醒监听"这种编号日志，排查从小时级降到分钟级，这算是我最自豪的工程化细节；
② 车控配置驱动——新车型加功能只改 JSON 不用发包；
③ 全链路流式——首字延迟压到 0.3s。建议讲②或③，因为①的"日志"容易让面试官觉得在炫技，②③更体现业务价值。
深挖反过来，最失败、最想吐槽自己的是什么？
考察：反思能力、诚实度
说实话，最想吐槽的是早期"布尔变量满天飞"那版——isWakeuping、isStartingSpeechRecognition、isTTSSpeaking 散在 Service 里，结果一堆状态组合 bug：TTS 播着播着 ASR 又开录，把 AI 自己的声音录进去自问自答。后来才下决心重构成状态机。教训是：多线程 + 异步回调的系统，第一版就该上状态机，别信"先跑起来再说"。

B2 架构与设计模式

🎬 先听整体主流程 → 🔍 追问分层与通信 → 🕳️ 深挖状态机/配置驱动细节 → 🚀 最后问重构意愿。
开场你整个语音助手的主流程能画个图讲讲吗？
考察：全局视角
可以。就一条主线：待唤醒 → 唤醒 → 识别 → 理解 → 执行/回答 → 再待唤醒。
① 开机自启拉起 MainActivity → 申请权限 → 绑定 Service；② Service 里先初始化鉴权（拉阿里云 Token）和 TTS，然后初始化本地唤醒，进入 WAIT_WAKEUP；③ 说"小云小云" → 切 WAKEUP_SUCCESS → 播"你好，请说" → 切 ASR 监听 WAIT_REGON；④ ASR 出最终结果 → 走命令优先级链（退出 > 车控 > App 控制 > 可见即可说 > 音乐 > AI 问答）；⑤ AI 问答走 LLM 流式 + 流式 TTS，播完自动回下一轮 ASR（多轮对话）。副线还有：网络断/连自愈、模型切换、离线语音包预下载。
追问为什么拆了三个 Service？全堆一个里不行吗？
考察：服务拆分依据
三个理由：① 职责——VoiceAssistantService 编排核心逻辑，FloatingChatService 管悬浮气泡 UI，MyAccessibilityService 管系统导航/节点抓取，各管一摊；② 前台服务类型隔离——核心服务声明 microphone，悬浮窗声明 phoneCall，Android 14+ 对前台服务类型查得很严，混在一起会被系统拒绝；③ 故障隔离——无障碍服务被系统重启不影响语音主流程。这也算模块化的一个缩影。
开场你这语音助手的状态机具体怎么实现的？内部逻辑是什么？怎么确保它不出错？为什么用状态机而不是 if/else？
考察：状态机必要性 + 正确性保障
说实话，这个是被 bug 逼出来的。最早我拿一堆布尔变量拼：isWakeuping、isStartingSpeechRecognition、isTTSSpeaking 全散在 Service 里。结果就是各种"卡死"反馈——要么唤醒成功了识别却起不来，要么 TTS 还在播，ASR 又开录了，把 AI 自己说的话当用户指令录进去了，直接自问自答（笑）。后来我痛下决心，把整个助手收敛成一个 4 态的有限状态机。
状态定义：WAIT_WAKEUP（只挂唤醒词，不干别的）→ WAKEUP_SUCCESS（刚被唤醒，准备切识别）→ WAIT_REGON（正在听用户说话）→ REGOIN_SUCCESS_AND_RETRY（这轮答完了，等下一句或超时回唤醒）。
核心逻辑：所有异步回调——唤醒回调、ASR 中间/最终结果、TTS 播完回调、网络回调、模型切换事件——进来第一件事就是 if (assistantStatus != 期望值) return，状态不对直接拒掉，从源头掐断并发竞争。
怎么确保正确：三招。第一，状态转移只有一条主线，单向推进，谁想改状态必须先通过前置校验；第二，全项目十几个进入状态的入口，每个我都打了唯一编号日志（"第 N 个进入等待唤醒监听方法的入口"），出 bug 拉日志一眼定位是从哪条路进来的，排查从小时级降到分钟级；第三，关键资源再加一道互斥——startASRListening() 是 synchronized 的，配合 isStartingSpeechRecognition 标志位防重入。
为什么不用 if/else：因为状态太多了——唤醒中、识别中、播报中、等待中、切模型中，互相组合，布尔变量根本理不清；而且这些回调来自不同线程，你不知道它什么时候来。状态机把"此刻能不能做这件事"收敛成一个判断，这是我踩完坑换来的教训。
追问你 Service 和 Activity 之间怎么通信的？为什么要用 Binder？
考察：IPC 选型
用了 ServiceConnection + LocalBinder：Activity 绑定服务后拿到 voiceService 对象引用，同步调 isServiceActive()、startASRListeningWithoutWakeup()。为什么不用 Messenger/AIDL？因为这是同进程通信，Binder 直接给对象、方法调用零开销；Messenger/AIDL 是为跨进程设计的异步方案，这里用了反而多余。我判断标准很简单：同进程用 Binder，跨进程才上 AIDL。
追问为什么用 EventBus？广播、单例回调不好吗？
考察：通信选型
EventBus 适合这种"单 App 内、跨组件、消息种类固定"的场景：① 解耦——VoiceAssistantService 发事件，FloatingChatService、ChatActivity 各订阅各的，互不引用；② 线程切换——@Subscribe(threadMode = MAIN) 直接回调主线程，省得自己 post；③ 比广播快（进程内直接分发，不走 Binder）。它有个前提：必须同进程，跨进程得换广播/Service。本项目所有通信都在进程内，EventBus 正好。单例回调的问题是要么全局一把梭、要么层层传，EventBus 把"谁关心谁订阅"表达得更清楚。
深挖车控为什么要搞成配置驱动（JSON）？直接硬编码不更快？
考察：可扩展性意识
硬编码快是快，但车机项目的痛点在于车型多、口语说法多、迭代快：① 同一个动作"开空调"，用户可能说"打开空调""把空调开一下""启动空调"，每种说法一条正则，全写死在代码里，改一次发一次包；② 新车型功能不同，改 JSON 就能适配，不用动代码；③ 测试和产品也能直接改配置调优，不用找我。所以我把 car_commands.json 做成"设备-操作-触发正则-动作-反馈"四层结构，这是典型的数据驱动设计。
深挖"打开空调和关闭车窗"这种复合指令，你代码里怎么拆的？
考察：复合指令处理
三步：① 分隔——按"和/与/并且/同时/以及/还有/并"这几个连接词拆成子句（COMPOUND_SEPARATORS）；② 动词补全——用户说"开空调和车窗"，第二个子句"车窗"缺动词，我就从第一个子句借前两个字补成"开车窗"；③ 逐条匹配执行——每个子句独立走命令匹配，都命中了就并行执行，反馈文本用"，"拼接。还有个防误判细节：只要有一条子句不是有效车控指令，整个就不返回结果，避免"我和谁吃饭"这种被误拆。
深挖中文数字"二十六度"怎么转成 26 的？
考察：算法细节
两步：① 正则提取——先匹配"最大/最高/最小/最低"这类极值词，再匹配"零一二三...十百千万 + 度/档"提取出"二十六"；② 中文数字转阿拉伯——我写了个解析器，倒序遍历字符，数字字符累加、单位字符乘算（十=10、百=100），"二十六"就是 2×10+6=26，还要处理"十"前面没数字的情况（默认 1，就是"十"=10）。最后分别映射：空调温度范围 16-32°C、风速 0-8 档，超范围直接语音反馈"超出范围，无法执行"。
升华如果给你一个月，让你重写这个项目，你会怎么改？
考察：反思与视野
我会做四件事：① 把 2856 行的 VoiceAssistantService 拆成模块——WakeupEngine / ASREngine / TTSEngine / LLMEngine / CommandRouter，用接口解耦；② LLM 流式改用原生 OkHttp + SSE 实现，不再依赖闭源 llmclient.aar，方便私有化部署；③ 状态机换成 Kotlin 的 StateFlow + 编译期校验，把"非法状态转移"变成编译错误而不是运行时 bug；④ 补上埋点上报（唤醒率、ASR 错误率、首字延迟 P99），让质量可度量。核心目标：从"能跑"到"可观测、可测试、可替换"。

B3 语音唤醒 KWS

🎬 唤醒整体怎么做的 → 🔍 为什么本地跑、怎么和 ASR 抢话筒 → 🕳️ 失败重试的坑。
开场唤醒是怎么实现的？
考察：KWS 方案
基于阿里云 NUI SDK 的本地唤醒：NativeNui.startDialog(Constants.VadMode.TYPE_ONLY_KWS)，配合 assets 里的 WakeUp.bin 模型（初始化时拷到本地工作目录，用 upgrade_file 指向它）。SDK 识别到唤醒词会触发 EVENT_WUW_TRUSTED 事件，我从 kwsResult.kws 的 JSON 里解析出"小云小云"，然后通知服务层切换状态。唤醒词是支持自定义的（wuw 参数里可以传多个词），默认"小云小云"。
追问为什么唤醒词要在本地跑？云端不是识别率更高吗？
考察：本地 vs 云取舍
唤醒词这个场景，本地是刚需：① 延迟——唤醒词必须毫秒级响应，云端来回一趟网络至少几百毫秒，用户会觉得"叫不动"；② 可用性——车在地库、隧道没信号，唤醒必须能用；③ 隐私——唤醒词是持续监听的，全量传云端有隐私风险。云端方案我了解，效果确实更好（多麦克风降噪、抗噪），所以我把唤醒做成"本地优先"，等唤醒成功进入识别阶段再视网络切在线/离线。
深挖唤醒和识别不能同时录音，你怎么做到无缝切换的？
考察：资源切换
这个坑很典型：一个 AudioRecord 只能被一个引擎用，唤醒和 ASR 同时开必炸。我的做法：① 唤醒成功 → stopRecognize() → SDK 回调 STATE_CLOSE → 释放唤醒的 AudioRecord；② 唤醒引擎的 HandlerThread quitSafely() 退出；③ 全新创建 ASR 引擎的 AudioRecord（走 AliyunASRUtil 或 XunfeiOfflineASRUtil）。配合状态机 WAIT_WAKEUP → WAKEUP_SUCCESS → WAIT_REGON 单向推进，保证任意时刻只有一个录音源活着。
深挖唤醒初始化失败、或者 SDK 报错，你怎么处理的？
考察：异常容错
分三种：① AudioRecord 初始化失败——重试 3 次，带退避延迟；② 鉴权文件没下载（错误码 240088/240070）——这常见于首次装车没网，这种不重试，等网络回调恢复后自动重新初始化；③ SDK 状态不对（240007）——必须先 cancelDialog() 把 SDK 拉回 idle 再重试，否则卡死恢复不过来。另外我维护了一张 20+ 条的错误码映射表，把 140008/240066/41010105 这些码都翻译成人话，方便车上现场定位。

B4 ASR 语音识别

🎬 用的哪家 ASR → 🔍 在线/离线怎么切 → 🕳️ 重复启动、回声、缓冲区这些坑 → 🚀 错误体系。
开场ASR 用了哪家的？为什么用两套？
考察：方案选型
两套：阿里云 NUI 在线 ASR（wss://nls-gateway.cn-shanghai.aliyuncs.com，上海/深圳双地域，识别率 95%+）+ 讯飞 AIKit 离线 ASR（ee62fa27c 中英听写能力）。为什么要两套？车机场景网络不是恒定的：市区有网用在线（效果最好），地库、隧道、偏远地区断网就切离线（还能继续识别），两套共用同一个 IASRUtil 接口，业务层无感切换。这也是 POC 要验证的核心问题之一：离线能不能顶住。
追问在线和离线怎么切换？什么时候用哪个？
考察：配置与兜底
两处判断：① 配置开关——ConfigManager.getASREngine() 从车机外部配置文件读 ASR_ENGINE=online/offline，可以在不重装的情况下切引擎（测试现场也方便）；② 运行时网络兜底——在线模式下，唤醒成功后发现没网，直接播报"无网络连接"并回待唤醒，不会傻等；离线模式则根本不依赖网络，LLM 那步再单独做联网检查。切换成本很低，因为两个引擎都实现了 IASRUtil，接口一模一样。
深挖怎么防止 ASR 重复启动？这种问题实际遇到过吧？
考察：并发控制
遇到过，而且很典型。当时是：TTS 播完回调要启动下一轮 ASR，同时用户又说了话触发另一个启动路径，两个线程同时进 startASRListening()，结果开了两个识别会话。我的防护是三层：
① synchronized startASRListening()——方法级互斥，同一时刻只有一个线程能进；
② isStartingSpeechRecognition 标志位——进了就置 true，返回前统一 reset，防止重入；
③ 状态机前置检查 isASRListeningAllowed()——如果当前是 WAIT_REGON（正在识别）就直接 return，从业务语义上就不允许重复启动。
还有一层工程细节：这个标志位全项目有 8 处赋值，我每处都打了编号日志（"设值处 N"），出问题能看出是谁改的、什么时候改的。
深挖怎么避免把 TTS 的声音录进 ASR？
考察：声学回声消除
三层防护：① 硬件/系统级回声消除——AudioRecord 初始化时对 session 开启 AcousticEchoCanceler；② 音源选择——Android 10+ 用 MediaRecorder.AudioSource.VOICE_COMMUNICATION，这是通话级音源，自带降噪；③ 业务互斥——最硬的一层：TTS 一开始播，我立刻 asrUtil.stopRecognize() 把识别停掉，播完再开。为什么需要第三层？因为 AEC 只能消掉喇叭直出的声音，车里声音复杂（风噪、发动机、人声混响），纯靠 AEC 不保险，状态机互斥才是根治。
深挖ASR 的缓冲区、录音文件这些细节，你踩过什么坑？
考察：健壮性细节
几个小坑：① 队列满——音频帧进 LinkedBlockingQueue，满 100 帧就丢最老的（优先保最新）；② 缓存超时——SDK 还没给 taskId 时音频先缓存，5 秒没消费就清空，避免残留脏数据；③ 并发写文件——"文件已关闭还在写"的崩溃，我用 audioFileLock 同步块把文件打开/写入/关闭串行化；④ 空文件——没有 taskId 不创建文件。这些小问题单个看都不起眼，但车载长跑环境下（连续监听几小时）任何一个都可能偶发崩溃。
升华ASR 的错误码体系你怎么设计的？
考察：错误处理设计
统一走 getMsgWithErrorCode 映射表：20+ 错误码 → 中文提示 + 三个行为标记（是否 Toast、是否朗读、是否重启识别）。特殊错误单独处理：SILENT_SPEECH（用户超时没说话）→ 1 秒后隐藏气泡回待唤醒，不打扰；鉴权类错误（240088/140008）→ 不重试，等网络恢复自愈。我刻意把"错误处理"和"业务逻辑"分开，所有引擎的错误都归一成同一套回调，业务层只关心 onError(msg, showToast, restart) 三个参数。

B5 TTS 语音合成

🎬 TTS 怎么选的 → 🔍 流式播报的实现 → 🕳️ 取消、声线、语音包这些细节。
开场TTS 你用的什么方案？为什么流式 + 离线两套？
考察：场景化设计
三套，各有分工：
① 在线流式 TTS（AliyunStreamUtil，声线 zhixiaoxia）——AI 回答专用，边生成边播，首字 0.3s；
② 离线 TTS（AliyunOfflineTTSUtil，默认声线 aijia）——启动时那句"你好，请说"、车控反馈这些必须 100% 能播的，断网也要响；
③ 系统 TTS（SystemTtsManager）——最后兜底。
为什么离线要单独一套？因为在线 TTS 首次需要下载鉴权文件，没网会失败，车控反馈"车窗已打开"这种话如果播不出来，用户会以为没执行。
开场流式播报是怎么播出来的？怎么实现边生成边说话？
考察：流式链路 + 体感优化
这个我踩的坑最深。最早我做的是"等 AI 完整生成一整段 → 一次性丢给 TTS 合成 → 合成完再播放"，结果用户问完一句话，屏幕要干等两三秒才出字、三四秒才出声，体验非常差，评审会上被直接打回。
后来改成全链路流式，三层都在流：
① 大模型流式返回——用 llmclient 的流式服务（SSE 那种），AI 每生成一小段就回调一次 onChunk；
② 流式 TTS——把阿里云 NUI 的 TTS 切到流式输入模式（MODE_STREAM_INPUT_TTS），拿到 chunk 直接 sendStreamInputTts(chunk) 推给云端，云端边合成边往回推 PCM 音频，通过 onStreamInputTtsDataCallback 实时回调；
③ AudioPlayer 边收边放——底层是 AudioTrack，数据进来就写缓冲区开始播，不用等整段合成完。
所以用户体感是：AI 才说到一半，声音已经出来了，首字延迟压到 0.3 秒左右，浮窗文字也同步滚动。入口在 VoiceAssistantService.queryQianwen，onChunk → streamUtil.speak(chunk)。
还有个关键工程细节：TTS 一开始播，我立刻 stopRecognize() 把 ASR 停掉——不然麦克风会把喇叭里 AI 的声音录进去，当成用户下一句话识别，AI 就开始自问自答了。这是上线第一天就翻过的车（苦笑）。
深挖TTS 取消时，你靠什么保证状态不残留？
考察：并发与状态一致性
这个我专门处理过，因为 SDK 的取消回调是异步的，你发了 cancel 它可能过几百毫秒才回调，这时候如果直接复用 TTS 实例，可能播到一半的音频还在往外吐。我的做法：① cancelStreamInputTts() 发取消；② 立即 audioPlayer.stop() 停播放；③ synchronized { isSynthesizing = false; } 强制同步标志位——代码注释里我写的是"无论成功与否，强制同步状态（避免 SDK 回调延迟导致的状态不一致）"。这套"发取消 + 主动停 + 强制同步"三连是踩过坑总结出来的。
追问离线语音包（声线）你是怎么管理的？
考察：资源管理
离线 TTS 的声线是分语音包打包的：阿里云 aar 自带一个 aijia，够用但只有一种声音。我加了启动时预下载：downloadOfflineSource() 在 Service.onCreate 里异步拉取 xiaoqi（温柔女声）等 zip 包，解压到模型目录。初始化时 checkOfflineVoicePackage() 检查目标声线是否存在，不存在就回退到自带的 aijia，保证"永远有声音可用"。下载失败只是没有新声线，不影响主流程——这类降级设计车机上到处都是。

B6 LLM 集成与流式

🎬 接了几个模型怎么封装 → 🔍 切模型、结构化输出 → 🕳️ 竞态、重试 → 🚀 延迟优化。
开场你接了几个大模型？怎么封装的？
考察：可扩展架构
三个：千问（dashscope SDK）、豆包（火山引擎 Ark SDK）、芯擎端模型（私有 SDK，车机本地推理）。封装上我做了两层抽象：
① ILlmClientStreamService 接口 + StreamCallback 回调——三个模型各自实现，业务层不关心底层是哪个；
② createStreamServiceByModel 工厂——按模型名创建对应实现。
另外还留了一条非流式回退 TongyiQianwenUtil（自实现 OkHttp + 指数退避重试），保证流式通道异常时还能出结果。选模型是按推理能力和速度排的：qwen-max 最强、qwen-plus 均衡、qwen-turbo 最快，代码里都给了注释。
追问回答到一半，用户切模型，你怎么办？
考察：热切换竞态处理
这是我最怕的竞态场景之一。流程：① 收到 EVENT_SWITCH_MODEL 事件，先 removeCallbacks 掉上一个还没执行的切换任务（防连点）；② 停 TTS、streamClient.cancelCurrentRequest() 取消当前流式请求；③ 关键——等 300ms 让 SDK 的 onCancel 回调落地（onCancel 里会置 isCancelTask=true）；④ 确认取消完成后再换 currentStreamService 并重新 set；⑤ 用缓存的 lastValidQuestion 直接重发请求，用户看到的是"已切换到豆包，正在重新回答"。
如果不等 onCancel，新请求和旧请求的回调会串，屏幕上可能同时滚两个模型的答案。这也是"取消类回调必须等完成"的一个实战案例。
追问LLM 返回的导航/音乐/图片这些结构化内容，你怎么解析的？
考察：多模态输出
约定协议：LLM 输出带前缀的结构化字段，客户端按前缀路由。比如导航：navi:{"endLongitude":"116.39","endLatitude":"39.91","poiName":"天安门"} → 解析成 NavigationData → 调起导航 App；音乐：play_music;歌名 → 走 QQ 音乐 URI 播放；图片：onImageAttachment 回调里 base64 先存 MMKV（用时间戳做 key），再发事件让浮窗 Glide 加载。在 StreamCallback 里我拆了 6 个独立回调（文本/食物/景点/音乐/导航/图片），各订阅各的，互不干扰。
深挖LLM 请求失败、超时，你怎么重试？
考察：可靠性
enqueueRequest 里做了两层：① 网络异常——ConnectException / SocketTimeoutException 区分连接超时和读取超时，指数退避（1s、2s）最多重试 2 次；② HTTP 错误——5xx、429 才重试，4xx 不重试（那是请求本身的问题，重试也没用）。三次都失败就回调错误：语音播"这个问题我不太会呢"，状态回待唤醒。超时参数也调过：连接 5s、读取 15s、写 5s，单次请求总预算约 13 秒，再久用户就烦了。
升华首字延迟从 2-3s 压到 0.3s，除了流式还做了什么？
考察：性能优化链路
流式是主因，但配套做了三件事：① 连接复用——OkHttp 配了连接池（5 个空闲连接保 5 分钟），避免每次握手；② 提前初始化——流式 TTS 在服务启动时就预创建，第一个 chunk 来了直接用，不用现建；③ UI 先出"思考中"——LLM 还没返回前浮窗先显示状态，用户感知上"有响应"。延迟优化从来不是单点，是链路每一环的累积。

B7 车控

🎬 车控怎么调到硬件 → 🔍 3D 可见即可说的特殊性 → 🕳️ 边界、测试。
开场车控具体是怎么调到车窗、空调的？
考察：核外能力
走的是公司自研的 CarControlSDK（com.fii.foxconn.carcontrolsdk）：CarControlManager.getInstance().init(context) 初始化，等 isReady()（我做了 0.5s 超时轮询），然后调 setWindowState(WINDOW_FRONT_LEFT, STATE_ON)、getACTemperature(AC_AREA_LEFT) 这类接口，返回 0 表示成功。SDK 底层是透传到车机的整车控制器（CAN 总线那层），我们应用层只拿封装好的语义接口。另外因为我们是系统签名应用，还能干普通 App 干不了的事，比如 forceStopPackage 反射杀进程。
追问3D 界面上的"可见即可说"和 2D 有什么不同？
考察：2D/3D 机制差异
核心差异：2D 是控件树，3D 不是。
2D：无障碍服务能拿到 AccessibilityNodeInfo 节点树，有文字有坐标，能直接点击。
3D：Launcher 的 3D 场景是引擎渲染的 Mesh，无障碍根本抓不到。所以 3D 走的是"反向推送"：3D Launcher 通过车控 SDK 的 onCallBackVoiceAssistant 回调，把当前可见的 3D 元素（车模、氛围灯、充电口）打包成 JSON 推给我们，我们存列表；语音匹配到元素名后，调 setVoiceCommandToAndroid 让 Launcher 自己执行点击。一句话：2D 是我"抓"界面，3D 是界面"送"给我。
深挖温度 16-32、风速 0-8 这种边界是怎么定的？超了会怎样？
考察：边界与用户体验
这是跟整车确认的硬件能力范围：空调温度 16-32°C、风速 0-8 档。我在执行前做校验，超范围直接语音反馈"温度超出范围，无法执行"，不会真的发指令给整车（避免误操作硬件）。还有一个细节：调温度是"相对值"——用户说"调高两度"，我会先 getACTemperature 读当前值，加 2 后再校验 16-32，而不是无脑执行。这套逻辑在 executeCarControl 里，注释都标了。
升华复合指令、"二十六度"这些 NLP 细节，你测试怎么覆盖？
考察：测试意识
① 单元测试——CarControlUtil.processCarCommand 是纯逻辑，可以脱离真车测：喂"打开空调和关闭车窗""二十六度""调高两度到 32 度"，断言返回的反馈文本；② 边界用例——中文数字全覆盖（零到万）、极值词（最大/最高）、超范围（35 度）、无参指令、误拆场景（"我和谁吃饭"）；③ 集成测试——车上实测每个设备每种说法，正则匹配失败的现场改 JSON 即可。测试设计的关键是：把"语言理解"和"硬件执行"分层，前者可以完全 mock 掉真车。

B8 可见即可说 / 无障碍

🎬 可见即可说整体怎么做 → 🔍 匹配与兜底细节 → 🕳️ 服务被杀、性能问题。
开场"可见即可说"具体是怎么实现的？
考察：核心机制 + 2D/3D 差异
说白了就是：屏幕上显示什么，你念什么就能点什么。车机上有两块屏幕场景，做法完全不一样。
2D 原生界面（基于无障碍服务）：无障碍服务会收到窗口切换、内容变化的系统事件，我先做 300ms 防抖避免高频刷新，然后 getRootInActiveWindow() 拿到整棵控件树，深度优先遍历，把"用户可见、有文字、有坐标"的节点都收进内存列表（比如按钮文字"蓝牙设置"、坐标 (x, y)）。等用户说"打开蓝牙设置"，ASR 出结果后做模糊匹配——先去标点空格，再把中文数字统一成阿拉伯数字（"第三页"和"第3页"必须能对上），匹配上了就对这个节点执行 performAction(CLICK)；有些控件不响应标准点击，我就用 dispatchGesture 在它中心坐标模拟一根手指点下去，这是兜底。
3D 场景（Launcher 3D 引擎）：3D 界面不是控件树，无障碍根本抓不到，比如车模、充电口、氛围灯这种。车机 3D Launcher 会通过车控 SDK 的回调，把当前屏幕上"可见的 3D 元素"打包成 JSON 推给我们（onCallBackVoiceAssistant），存成 visible3DElements 列表；语音匹配到元素名，再调 setVoiceCommandToAndroid 回给 Launcher 让它自己执行点击。
还有个细节：2D 和 3D 是分优先级串行处理的——先试系统导航指令（"返回上一页""回桌面"），再试 2D 节点，最后试 3D 元素，避免"返回"这种词被误当成按钮点了。
追问为什么还要 dispatchGesture 坐标点击？performAction 不就行了吗？
考察：兼容性处理
因为我实际遇到 performAction(CLICK) 失败的三种情况：① 节点虽然可点但事件被父容器拦截；② 节点 isClickable=false 但 bounds 有效（很多自绘控件）；③ 车机厂商魔改了无障碍事件分发。坐标点击 dispatchGesture 是模拟真实手指，在系统层面更"底层"，成功率更高。我的策略是先标准点击、失败再坐标兜底，双保险。但坐标点击也有缺点：依赖屏幕坐标，屏幕旋转/缩放后就失效，所以只能当 fallback。
深挖无障碍服务被系统杀了、或者用户关了，怎么办？
考察：降级与引导
分三层：① 检测——MainActivity 启动时用 AccessibilityUtils 检查服务是否启用，没启用弹引导跳设置页；② 降级——运行中 MyAccessibilityService.getInstance() == null 就直接跳过 2D 匹配（3D 和车控不受影响），不会崩；③ 资源回收——onInterrupt / onDestroy 里把抓到的节点全部 recycle() 防泄漏。可见即可说属于"锦上添花"功能，挂了不能拖累主流程，这是底线。
深挖遍历整棵控件树，会不会卡 UI？
考察：性能意识
会，所以做了四件事：① 300ms 防抖——TYPE_WINDOW_CONTENT_CHANGED 事件很频繁，合并成一次刷新；② 只收可见节点——isVisibleToUser 过滤，屏幕外的直接跳过；③ 子节点 recycle——遍历完立即回收，防止节点对象堆积导致的内存问题；④ 深度排序 + 命中即返回——深层节点优先匹配，一般第一二个候选就命中了，不会全表扫完。说实话在大屏车机上节点多时还有优化空间（比如缓存窗口 hash），但当前规模下已经够用。

B9 导航与多 App 联动

🎬 导航怎么调起 → 🔍 音乐怎么控制 → 🕳️ 失败兜底。
开场导航是怎么调起来的？高德百度都支持？
考察：URI Scheme 与跨 App
靠 URI Scheme 跳转，写了 AMapNaviUtils：① 高德路线规划 amapuri://route/plan/?sourceApplication=FiiCarAIVision&dlon=...&dlat=...&dname=...；② 高德直接导航 androidamap://navi?lon=...&lat=...&dev=1&style=2（dev=1 表示坐标需要国测加密）；③ 百度导航 baidumap://map/navi?query=...&location=lat,lon&coord_type=gcj02。LLM 返回 navi: 字段就走百度（测试账号有百度 key），导航列表选择走高德（预装的高德）。每条路径都先 resolveActivity 判断有没有 App 能处理，避免 ActivityNotFoundException 崩掉。
追问音乐控制怎么做的？不同音乐 App 怎么兼容？
考察：媒体交互
两条路：① 通用方案——AudioManager.dispatchMediaKeyEvent 派发 KEYCODE_MEDIA_NEXT/PREVIOUS/PLAY/PAUSE，谁持有媒体焦点谁响应，任何音乐 App 都认；② QQ 音乐车机版专属——它提供 qqmusiccar:// scheme，支持搜索点歌：qqmusiccar://?action=8&mb=true&m1=true&search_key={base64(歌名)}，歌名要 Base64 编码避免 URL 转义问题。为什么两套？通用方案只能切歌暂停，做不到"播放某首歌"，点歌必须走专属 scheme。这算跨 App 深链集成的典型做法。
深挖App 没装、或者跳转失败，你怎么兜底？
考察：健壮性
① 跳转前先 Utils.isAppInstalled() 检查包名，没装直接语音提示"没有安装 QQ 音乐车机版"，不会傻跳；② resolveActivity 再确认一遍；③ 外层 try-catch，异常时播报"加载导航失败"并回待唤醒；④ 成功启动导航后我会立刻退出语音监听（切回待唤醒），避免导航语音被我的 ASR 录进去。还有一个细节：queries 里显式声明了高德包名，Android 11 的包可见性才放行。

B10 系统集成与稳定性

🎬 系统签名怎么配 → 🔍 保活、网络自愈、音频焦点 → 🕳️ 兼容性坑。
开场系统签名 + platform 这套是怎么配的？
考察：系统级应用
三件套：① Manifest 里 android:sharedUserId="android.uid.system"——共享系统进程身份，App 就能拿到系统级权限；② 签名用平台 key——key/se1000.jks，alias 是 platform（这是车机厂商提供的平台签名，普通开发者签不了）；③ build.gradle 里 signingConfigs.myrelease 同时给 release 和 debug 用（必须同一把 key，否则升级会报签名冲突）。有了这套，我们才能拿 READ_PRIVILEGED_PHONE_STATE、绕过后台限制、反射调 forceStopPackage。这是车机 IDH/ODM 项目的标配玩法。
深挖前台服务被系统 kill 了，你怎么拉回来？
考察：保活
三层：① onStartCommand 返回 START_STICKY——被 kill 后系统会尝试重建；② onDestroy 里注册 AlarmManager 5 秒后 PendingIntent 再启动服务——AlarmManager 比 START_STICKY 更可靠，因为 PendingIntent 是系统级闹钟；③ 极端情况 restartApp——用 AlarmManager 拉 MainActivity + Process.killProcess + System.exit(0) 自杀重启（这招主要是 NUI 鉴权文件 bug 触发，正常情况下用不到）。坦白说车机上系统内存紧张，进程被杀很常见，这套"STICKY + Alarm + 自愈"是必须的。
深挖网络断了、恢复了，你怎么自愈？
考察：链路自愈
用 ConnectivityManager.NetworkCallback 监听：
onLost（断网）：置 isNetWorkAvailable=false，4 秒后强制回待唤醒 + 重启唤醒监听——为什么延迟 4 秒？因为用户可能正说到一半，不能立刻打断；
onAvailable（恢复）：① 重新拉 token；② 重新初始化 TTS——首次装车没网时 TTS 鉴权文件下载会失败（140008），断网恢复后必须重试；③ 4 秒后重启唤醒。
这套自愈逻辑处理了 POC 期间最头疼的"第一次装车没网导致语音起不来"问题，现在断网恢复后全程无人值守自动恢复。
追问音频焦点怎么管的？导航播报会不会被地图声音打断？
考察：音频策略
AudioFocusManager 用 AUDIOFOCUS_GAIN_TRANSIENT_EXCLUSIVE——这是最严的独占型焦点，适合语音识别/播报场景。回调里处理四种情况：GAIN（拿回焦点继续）、LOSS（永久丢失，停）、LOSS_TRANSIENT（临时丢失，停）、LOSS_TRANSIENT_CAN_DUCK（可以降低音量让路）。实际场景：地图播报"前方拥堵"时会抢走焦点，我收到 LOSS 就停 TTS；地图播完了焦点回来我继续。唤醒监听启动前会先释放焦点（ABANDON_AUDIO_FOCUS），避免录音时跟音乐打架。
追问开机自启怎么做的？
考察：开机链路
BootCompletedReceiver 监听 ACTION_BOOT_COMPLETED 和 QUICKBOOT_POWERON（部分车机快速启动走这个），priority 设 1000 抢优先接收。收到广播后启动 MainActivity（带 FLAG_ACTIVITY_NEW_TASK，因为广播里启动 Activity 必须带这个 flag），MainActivity 再走正常流程：权限引导 → 绑定服务 → 前台服务 → 唤醒监听。为什么不直接广播里 startForegroundService？因为 Android 8+ 前台服务启动限制，而且权限还没申请，走 MainActivity 更稳。
深挖Android 13/14/15 的兼容性你踩过哪些坑？
考察：适配经验
挑典型的说：① Android 13 通知权限——POST_NOTIFICATIONS 必须动态申请，不然前台服务通知不显示；② Android 14 前台服务类型——foregroundServiceType 必须声明并匹配实际用途（microphone/phoneCall），不然启动直接抛 ForegroundServiceTypeNotAllowedException；③ Android 10 分区存储——外部配置文件改用 MediaStore API 读写（ConfigManager），不能直接写 /sdcard；④ Android 11 包可见性——<queries> 显式声明要查询的高德包名；⑤ 隐式 Intent——Android 14 对隐式 Intent 有更严格限制，跳转第三方 App 时该显式传 package 就传。这五个是我实际踩过的。

B11 并发与线程模型

🎬 用了哪些异步机制 → 🔍 防重入 → 🕳️ 切模型竞态、资源释放顺序。
开场项目里异步处理你用了哪些机制？
考察：多线程选型
五种，各有各的用途：① HandlerThread——唤醒/ASR 这类"后台长驻 + 主线程 post 任务"的场景（VoiceWakeupUtil、AliyunASRUtil）；② 主线程 Handler——mainHandler / switchModelHandler，UI 更新和延迟任务；③ SingleThreadExecutor——networkExecutor，网络请求串行池；④ EventBus——跨组件通信，自带 MAIN/BACKGROUND 线程切换；⑤ OkHttp 异步 enqueue——HTTP 请求自带回调线程。选择逻辑就一条：低频 UI 操作走主线程 Handler，高频后台任务走 HandlerThread，跨组件解耦走 EventBus，网络走 OkHttp。
追问ASR 启动你是怎么做防重入的？
考察：重入防护
三层：① synchronized 方法级互斥；② isStartingSpeechRecognition 标志位（进置 true 出置 false）；③ 状态机前置检查 isASRListeningAllowed()——正在识别（WAIT_REGON）就直接拒绝。还处理过一个特殊情况：标志位是 true 但 ASR 实际没初始化成功，这种"脏标志"我会强制重置，防止永远卡住。这个标志位全项目 8 处赋值，每处都打"设值处 N"编号日志，定位谁改的、什么时候改的，一眼就清楚。
深挖切模型时的 onCancel 竞态，你具体怎么处理的？
考察：竞态处理
经典竞态：取消请求是异步的，onCancel 回调还没到，新模型请求就发了，两个回调同时活着。我的方案：① 发 cancelCurrentRequest()；② switchModelHandler.postDelayed(..., 300)——留出 300ms 窗口等 onCancel 落地（onCancel 里置 isCancelTask=true）；③ 300ms 后检查 isCancelTask 是否为 true，没到就再等（带 2 秒超时强制重置）；④ 确认取消完成才换服务并重发请求。这个"取消必须等完成"的教训，后来我到处都在用。
深挖Service 销毁时，资源释放的顺序你怎么排的？
考察：生命周期管理
onDestroy 里顺序很重要，我按"先停新请求、再停引擎、最后收线程"：① 反注册 EventBus；② 置 isServiceActive=false（所有入口立刻拒绝新任务）；③ 移除 mainHandler 全部回调；④ 线程池 shutdown → awaitTermination(1s) → shutdownNow（留 1 秒优雅收尾，超时强杀）；⑤ 唤醒/ASR/TTS 各自 release（内部 HandlerThread quitSafely）；⑥ 网络回调反注册；⑦ 摄像头停止。最后再注册一个 5 秒 Alarm 自重启。每个资源释放都判空，避免二次释放崩溃。

B12 性能与可靠性

🎬 卡顿/内存问题怎么防 → 🔍 测试怎么做。
开场这种长驻服务，你最担心哪类性能问题？怎么防？
考察：性能意识
最担心三类：① 内存泄漏——长驻服务 + 异步回调，最容易泄漏。我的对策：统一用 ApplicationContext、Handler 静态内部类 + WeakReference（MainHandler 就是这么写的）、子节点及时 recycle；② UI 卡顿——无障碍遍历节点、GIF 切换、浮窗更新都收拢到主线程 Handler 串行化，高频事件防抖；③ 线程泛滥——网络请求收敛到单线程池，不 new Thread 满天飞。实测长跑几小时内存曲线平稳。
追问AudioRecord 长跑，你怎么保证不崩？
考察：资源管理
① 每次 start 前先 release 旧实例，防止"设备已被占用"；② 状态异常走 STATE_CLOSE 回调统一释放；③ 缓冲区大小用 getMinBufferSize 算出来再乘系数，防溢出；④ 录音数据写文件加锁防并发写；⑤ 初始化失败重试 3 次带退避，避免在车上"重启一次好一次"的玄学问题。车载环境音频设备竞争激烈（导航、电话、媒体都在抢），这套防护是实测出来的。
升华测试你怎么做？覆盖率到多少？
考察：测试能力
分三层：① 单元测试——车控指令（CarControlUtil）、中文数字转换、Token 签名（mock OkHttp）这些纯逻辑全覆盖；② 集成测试——真机/真车跑"唤醒 → 识别 → 车控 → 问答"全链路用例，断网/恢复、切模型、连续对话 5 轮这些场景脚本化；③ 性能监控——启动耗时、首字延迟、内存占用随手记录。坦白说覆盖率没到很高（车控类 80%+，Service 编排层低一些），因为 UI 和硬件耦合的部分自动化成本高，主要靠场景化手动测试补。面试时重点讲"哪些测了、哪些没测、为什么"比报一个虚假数字可信。

B13 调试与可观测性

🎬 怎么排查疑难 bug → 🔍 日志工程的理念 → 🕳️ 高频 bug 总结。
开场用户反馈"语音没反应"，你怎么排查？
考察：调试思路
按漏斗排查：① 先看状态——assistantStatus 是不是卡在某个状态了？看编号日志"第 N 个进入等待唤醒监听方法的入口"，确定是从哪条路进的；② 再看标志位——isStartingSpeechRecognition、isTTSSpeaking、isCancelTask 是不是被谁置 true 没复位（全项目每处赋值都有编号日志，能查到是哪行改的）；③ 再看链路——ASR 有没有出 onFinalResult？出了是走了命令链哪一支？被哪个前置命令抢了？④ 最后看网络/鉴权——是不是 240088 鉴权文件丢了？这套方法配合全链路编号日志，多数问题 10 分钟内定位。
追问为什么每个入口都要打"第 N 个"这种序号？
考察：日志工程理念
因为这个系统有 10+ 个"进入待唤醒"入口、7 个"启动 ASR"入口，它们代码长得几乎一样，肉眼根本分不清是哪条路触发的。带序号的 Log.w("----------第N个入口---------") 一秒定位触发路径。这是我特别想强调的一个工程习惯：日志不是记录"发生了什么"，而是记录"从哪来的"。多线程 + 状态机的系统，光看结果日志根本没法排查，路径日志才是关键。
深挖这项目里 Bug 频率最高的三类是什么？
考察：经验总结
① 状态/并发类——ASR 重复启动、TTS 与 ASR 互相干扰，占比最高，最后用状态机 + 标志位 + 互斥解决；② 资源类——AudioRecord 占用冲突、离线语音包没下载、缓存队列满，用重试 + 降级 + 预下载解决；③ 网络/鉴权类——首次装车没网导致鉴权文件缺失（140008/240088），用网络监听自愈解决。这三类其实也反推了架构该怎么做：状态机、降级策略、自愈机制——都是踩出来的。

B14 开放性问题

🚀 最后的高阶题：重写意愿、规模化、选型理由、国际化、价值观。
升华如果让你重写这个项目，你会怎么改？
考察：反思与视野
四件事：① 拆模块——2856 行的核心服务拆成 WakeupEngine / ASREngine / TTSEngine / LLMEngine / CommandRouter，接口解耦、单测友好；② LLM 流式改原生 OkHttp + SSE，摆脱对闭源 aar 的依赖，方便私有化部署和换供应商；③ 状态机用 Kotlin StateFlow + 编译期校验，把非法状态转移从运行时 bug 变成编译错误；④ 上埋点——唤醒率、ASR 错误率、首字延迟 P99，让"体验好不好"可度量。核心一句话：从"能跑"到"可观测、可测试、可替换"。
升华假设 1000 辆车上线，你这个架构扛得住吗？
考察：规模化思维
得拆开看：车机端本来就是单机架构，1000 辆车是 1000 个独立实例，不存在互相影响；真正的瓶颈在云端——阿里云 NUI、讯飞、大模型 API 的 QPS 和限流。要规模化得做：① 云端网关限流/排队，按用户等级分配；② 高频问题缓存（"今天天气"这类预渲染）；③ 离线优先——弱网场景走端模型（芯擎端模型就是为这个准备的），把云端压力导走；④ 监控 QPS、P99 延迟，容量规划。所以回答分两层：车机端没问题，云端要补限流和缓存。
升华为什么不用 Jetpack Compose 重写 UI？
考察：技术选型
这个项目 UI 占比很小——一个 ChatActivity + 两个悬浮窗 + 系统设置引导，XML 完全够用且调试工具成熟（车机分辨率、字体、HMI 适配都有现成方案）。Compose 的优势在复杂动态界面和团队长期迭代，这里成本收益不划算。但我说过，如果 ChatActivity 要继续做复杂对话流，值得迁——选型看场景不看潮流。
升华怎么支持海外车型 / 多语种？
考察：国际化
分四块：① 车控配置已按 carVersion 区分车型，海外版加配置即可；② 资源多语种——strings.xml + assets 多语言目录；③ 语音引擎换多语种模型——讯飞/阿里云都有英粤等多语种；④ LLM 换多语种 prompt 模板 + 路由。工作量主要在 ③④，架构上其实不用大改，这算是当初设计"引擎可插拔"的回报。
升华你觉得自己在这个项目里最有技术含量的设计是什么？
考察：亮点聚焦
我排三个：① 4 状态状态机 + 入口序号日志——把"多线程 + 异步回调 + 语音资源互斥"这个最难啃的硬骨头变成了可追踪、可复现的系统设计；② 车控配置驱动 + 复合指令 + 中文数字——用最朴素的工程手段（JSON + 正则 + 解析器）解决了"自然语言控制硬件"的问题，还没引入重型 NLP；③ 双 ASR + 三 TTS + 三 LLM 的可插拔设计——所有语音/模型能力都是接口抽象，换供应商只改一个实现类。这三个分别对应：正确性、业务价值、架构弹性。
升华最后聊聊：你觉得做车机语音和做手机语音，最大的不同是什么？
考察：行业认知
三个维度：① 环境——车内噪声复杂（风噪、发动机、空调），语音要抗噪、要处理回声，手机相对安静；② 离线刚需——地库、隧道、高速无网段，手机语音可以"等网"，车机语音必须"离线兜底"，所以唤醒、ASR、TTS 三块都要离线能力；③ 责任边界——车机语音控制的是"车窗、空调、导航"，误识别是有物理后果的（比如误开窗），所以命令匹配必须严谨（正则 + 边界校验 + 反馈确认），容错策略和手机完全不是一个量级。这也是我觉得这个项目最有价值的地方：它让我把"识别准不准"和"执行对不对"两个问题分开了。
